Normalización de bases de datos: 1FN, 2FN y 3FN con ejemplo completo

Normalización SQL explicada con dependencias funcionales, claves, primera, segunda y tercera forma normal y un ejemplo paso a paso.

2026-11-10 2 min de lectura

Normalizar una base de datos consiste en separar hechos que dependen de cosas distintas. El objetivo no es tener muchas tablas: es evitar que una modificación deje datos contradictorios, que una inserción requiera inventar valores o que un borrado elimine información que aún necesitas.

Respuesta directa. La 1FN exige valores atómicos; la 2FN elimina dependencias de una parte de una clave compuesta; la 3FN elimina dependencias transitivas entre atributos no clave. Antes de dividir tablas, identifica la clave y escribe qué atributo determina a cuál.

Una tabla que mezcla hechos

Imagina una tabla de matrículas:

alumno_idalumno_nombreasignatura_idasignatura_nombreprofesornota
17LucíaMAT101ÁlgebraMoreno8,1

a clave natural podría ser (alumno_id,asignatura_id)(alumno\_id, asignatura\_id)(alumno_id,asignatura_id). Sin embargo, lumno_nombredepende solo de lumno_id mientras que signatura_nombrey rofesordependen solo de signatura_id.

Primera forma normal

ada celda debe contener un valor indivisible para el modelo. Una columna elefonos con “600..., 700...” mezcla dos valores. Crea una tabla de teléfonos relacionada con alumno si necesitas almacenar varios.

Segunda forma normal

Con una clave compuesta, ningún atributo no clave debe depender solo de una parte. Separamos:

Alumno(alumno_id,alumno_nombre)\text{Alumno}(alumno\_id, alumno\_nombre)Alumno(alumno_id,alumno_nombre)
Asignatura(asignatura_id,asignatura_nombre,profesor)\text{Asignatura}(asignatura\_id, asignatura\_nombre, profesor)Asignatura(asignatura_id,asignatura_nombre,profesor)
Matricula(alumno_id,asignatura_id,nota).\text{Matricula}(alumno\_id, asignatura\_id, nota).Matricula(alumno_id,asignatura_id,nota).

Ahora la nota depende de la matrícula completa, mientras que los nombres están donde pertenecen.

Tercera forma normal

upón que Asignatura guarda rofesor_id rofesor_nombrey epartamento Si rofesor_iddetermina nombre y departamento, esos atributos no deben repetirse por cada asignatura. Crea una tabla rofesor(profesorid, profesornombre, departamento) y conserva la clave foránea en Asignatura.

Comprobar un diseño

Pregúntate qué sucede si cambias el profesor, añades un alumno sin matrícula o borras la última matrícula de una asignatura. Si el diseño obliga a actualizar muchas filas o hace desaparecer un hecho independiente, probablemente hay una dependencia mal ubicada.

La normalización no sustituye a pensar en consultas, índices y uso real de los datos, pero da una base fiable para hacerlo. Continúa con Python y SQL para empezar en datos o profundiza en la ruta de Python, SQL y Data Engineering.
